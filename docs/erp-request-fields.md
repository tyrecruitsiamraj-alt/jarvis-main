# Jarvis (So Recruit) อ่านอะไรจาก ERP บ้าง — หน้า "ข้อมูลใบขอ"

เอกสารนี้สรุปให้ทีมที่ดูแลฐานข้อมูล ERP เห็นชัดว่าระบบ Jarvis ไปหยิบข้อมูลอะไร
จากตารางไหน และกรองด้วยเงื่อนไขอะไร

**ปรับปรุงล่าสุด:** 7 ส.ค. 2569

---

## 1. สรุปใน 5 บรรทัด

* Jarvis **อ่านอย่างเดียว** — ไม่ INSERT / UPDATE / DELETE อะไรใน ERP เลยแม้แต่ตัวเดียว
* ข้อมูลที่ผู้ใช้ Jarvis แก้เอง (ผู้รับผิดชอบ · หมายเหตุ · สถานะทำงาน) เก็บในฐานของ Jarvis เอง คนละที่กัน
* ดึงเฉพาะ **ใบขอที่ยังหาคนไม่ครบ** ไม่ได้ดึงทั้งฐาน
* หนึ่งใบขอ = หนึ่งแถวบนหน้าจอ
* เรียกตอนผู้ใช้เปิดหน้าเว็บเท่านั้น ไม่มีงานเบื้องหลังที่ยิงตลอดเวลา

---

## 2. ตารางที่เข้าไปอ่าน

### ตารางหลัก (join กันตรง ๆ)

| ตาราง | ใช้ทำอะไร |
|---|---|
| `st_request_head` | ตัวใบขอ — เลขที่ วันที่ จำนวนที่ขอ จำนวนที่แจ้งเข้า สถานะ |
| `st_request_p2` | รายละเอียดที่ลูกค้าต้องการ — สถานที่ เพศ อายุ วันเวลาทำงาน **สัญชาติเจ้านาย** |
| `st_request_p3_rate` | อัตราจ่าย |
| `st_request_staff` | คนที่ลาออก / คนที่ถูกแทน |
| `ms_site` | ข้อมูลไซต์ — ชื่อไซต์ รหัสแผนก ประเภทสัญญา |

### ตารางที่เข้าไปอ่านชื่อ (lookup อย่างเดียว)

`ms_department` · `st_ms_contract_type` · `st_ms_request` · `hr_ms_staff_title` ·
`hr_ms_job_description_1` · `hr_ms_job_description_2` · `hr_ms_resign_type` ·
`wg2_ms_fee` · `hr_staff` · `st_site_contract_p1` · `st_request_p1` ·
`st_request_p3` · `st_inform_head`

## 3. ช่องบนหน้าจอ ↔ คอลัมน์ใน ERP

| ช่องที่ผู้ใช้เห็น | มาจากตาราง.คอลัมน์ |
|---|---|
| เลขที่ใบขอ | `st_request_head.request_no` |
| ชื่อผู้ส่ง | `hr_staff.fname + lname` (ผ่าน `st_request_head.do_id`) |
| วัน/เวลาที่ส่ง | `st_request_head.request_date` |
| วันที่ต้องการ | `st_request_head.want_date_from` |
| ขอมา | `st_request_head.request_qty` |
| หาได้แล้ว | `st_request_head.inform_qty` — ถ้าเป็น 0/ว่าง จะนับจำนวนใบใน `st_inform_head` แทน |
| คงเหลือ (ต้องหา) | คำนวณเอง = ขอมา − หาได้แล้ว |
| ทำงานวันสุดท้าย | `st_request_staff.resign_date` |
| ชื่อหน่วยงาน | `st_site_contract_p1.customer_name` (ผ่าน `st_request_head.contract_no`) |
| รหัสไซต์ | `st_request_head.site_code` |
| **สถานที่ปฏิบัติงาน** | **`st_request_p2.work_place1`** |
| สถานที่ทำงาน (ที่อยู่เต็ม) | `st_request_p2.work_place1` + `work_place2` + `work_place3` ต่อกัน |
| ลักษณะงาน | `hr_ms_job_description_1.job_description_name` |
| ตำแหน่ง (รายละเอียด) | `hr_ms_staff_title.staff_title_name` หรือ `hr_ms_job_description_2` |
| ช่วงอายุ | `st_request_p2.age` (เป็นข้อความ ระบบแปลงเป็นช่วงตัวเลขให้) |
| เพศ | `st_request_p2.sex` |
| **สัญชาติเจ้านาย** | **`st_request_p2.boss_nationality`** |
| ประเภทใบขอ | `st_ms_request.request_name` (ผ่าน `st_request_head.request_code`) |
| ชื่อคนลาออก | `hr_staff` (ผ่าน `st_request_staff.staff_id`) |
| สาเหตุที่ลาออก | `hr_ms_resign_type.resign_type_name` |
| รายได้ (อัตราจ่าย) | `st_request_p3_rate.payment_rate` |
| วันเวลาเข้างาน | `st_request_p2.work_date` + `work_time` |
| ชื่อผู้ติดต่อหน่วยงาน | `st_request_p1.contact_name` |
| เบอร์ติดต่อ | `st_request_p1.phone` |
| ค่าปรับกรณีขาดคน | `st_request_p3.abs_customer_fine` |
| แผนก | `ms_site.department_code` → `ms_department.department_name` |
| ประเภทสัญญา | `ms_site.contract_type_code` → `st_ms_contract_type.contract_type_name` |

**หมายเหตุ 2 ช่องที่เพิ่งเพิ่ม** (แถวตัวหนา) — เป็นคอลัมน์ที่อยู่ใน `st_request_p2`
ซึ่งระบบ join มาอยู่แล้ว จึงไม่ได้เพิ่มภาระ query ให้ฐานข้อมูลเลย

## 4. ใบขอแบบไหนที่ถูกดึงมา

ดึงเฉพาะใบที่เข้าเงื่อนไขครบทุกข้อนี้:

| # | เงื่อนไข | เหตุผล |
|---|---|---|
| 1 | `st_request_head.status = 'A'` | เอาเฉพาะใบที่ยัง Active |
| 2 | `is_stop = 'N'` และ `stop_no` ว่าง | ใบที่ถูก Stop แล้วไม่ต้องหาคน |
| 3 | `is_inform_all <> 'Y'` | แจ้งเข้าครบแล้วถือว่าจบ |
| 4 | ยังไม่มีใบแจ้งเข้าเลย **หรือ** แจ้งเข้าแล้วแต่ไม่ครบจำนวน | ใบที่ยังต้องหาคนต่อ |
| 5 | `request_code` เป็น `005` `006` `013` `014` | เอาเฉพาะประเภทที่ต้องสรรหาคนจริง ไม่เอาเปิดไซด์/เพิ่มอัตรา/ทีมเสริม |
| 6 | ตัดใบที่ชื่อลักษณะงานมีคำว่า "ทดแทน" | เป็นงานสรรหาภายใน ไม่ใช่ตำแหน่งของลูกค้า |
| 7 | ตัด `ms_site.contract_type_code = 'C'` | สัญญาเช่ารถอย่างเดียว ไม่มีงานหาคน |
| 8 | `department_code` และ `site_code` อยู่ในช่วงที่ตั้งค่าไว้ | จำกัดขอบเขต BU |
| 9 | กรองตามสิทธิ์แผนกของผู้ใช้ที่ล็อกอิน | คนแผนกหนึ่งไม่เห็นใบของอีกแผนก |

ข้อ 5–7 ใช้เฉพาะตอนดึงเป็นรายการ · ตอนเปิดดูใบเดียวจะใช้ข้อ 1–4 และ 8–9

## 5. เรื่องที่ควรรู้เพิ่ม

**หนึ่งใบขอมีอัตราจ่ายได้หลายแถว** — `st_request_p3_rate` มีได้หลายบรรทัดต่อใบ
ระบบเลือกมาแถวเดียวโดยเรียง `is_wage = 'Y'` ก่อน แล้วค่อยเอา `payment_rate` สูงสุด

**ความครบถ้วนของ 2 ช่องใหม่** (นับจากใบขอ 2 ปีล่าสุด 4,924 ใบ):

| ช่อง | มีข้อมูล | หมายเหตุ |
|---|---|---|
| `work_place1` | 4,909 ใบ (99.7%) | เกือบทุกใบกรอกครบ |
| `boss_nationality` | 1,949 ใบ (39.6%) | ในนี้เป็นขีด "-" อีก 408 ใบ |

`boss_nationality` เป็นช่องข้อความอิสระ คนกรอกเขียนได้หลายแบบ
(เช่น "ญี่ปุ่น" · "ญี่ปุ่น/ไทย" · "ญี่ปุ่น , ไทย" · "ญีปุ่น" · "คนไทย")
Jarvis แสดงตามที่กรอกมาตรง ๆ **ไม่แก้ไขและไม่จัดกลุ่มให้** ·
ถ้าอยากให้เอาไปกรอง/ทำรายงานได้ในอนาคต ต้องคุยกันว่าจะทำเป็นตัวเลือกตายตัวใน ERP ไหม

**สิ่งที่ Jarvis ไม่ได้ดึง** — ข้อมูลเงินเดือนรายคน · ข้อมูลส่วนตัวพนักงานนอกจากชื่อ ·
เอกสารแนบ · ประวัติการแก้ไขใบขอ

## 6. ปริมาณและความถี่

* ดึงเป็นรายการครั้งละไม่เกิน 2,000 ใบ (ปกติหน้าจอขอ 200)
* ยิงตอนผู้ใช้เปิดหน้าเว็บ ไม่มี job เบื้องหลังที่ยิงเป็นรอบ
* ใบขอที่ปิดไปแล้ว (สำหรับ Dashboard ย้อนหลัง) เก็บ cache ไว้ 10 นาที ไม่ยิงซ้ำ

## 7. ติดต่อ

มีคำถามหรืออยากให้เพิ่ม/ลดฟิลด์ไหน แจ้งทีม Jarvis ได้
ทุกอย่างเป็นการอ่านฝั่งเดียว ปรับได้โดยไม่กระทบข้อมูลใน ERP
